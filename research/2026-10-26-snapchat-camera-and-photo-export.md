# Snapchat camera, viewer, and Camera Roll repair

The supplied screenshot shows a landscape camera frame letterboxed inside the phone's portrait camera surface. The previous adapter removed Snapchat's exact 9:16 constraint but requested a square 1920×1920 stream. Its `contain` preview preserved the resulting frame; stretching that frame with `cover` would crop the face instead of recovering missing sensor content.

## Camera findings and implementation

- [W3C Media Capture and Streams, §4.3.8](https://www.w3.org/TR/mediacapture-streams/#constrainable-properties) specifies that constraints use the camera's primary orientation, while delivered settings can rotate with the device. WebKit's [AVVideoCaptureSource implementation](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/mediastream/cocoa/AVVideoCaptureSource.mm) transposes settings for rotated frames.
- [WebKit issue 323550, especially comments 4–6](https://bugs.webkit.org/show_bug.cgi?id=323550) records the counterintuitive iPhone behavior: requesting portrait dimensions can yield a landscape crop; requesting dimensions in the sensor's landscape orientation produces upright portrait frames. The first settings can also be stale until a frame arrives. This evidence changed the implementation from a portrait-shaped constraint to a primary-orientation constraint.
- [LiveKit's merged first-frame fix](https://github.com/livekit/client-sdk-js/pull/2100) independently addresses the initial-dimensions race. Vigil now waits for a decoded frame using a detached muted video consumer, with a bounded timeout and cleanup. It returns Snapchat's original stream, retains its device/microphone choices, and never makes a second capture request or stops the app's tracks.
- The request prefers 1920×1440 and 4:3 in primary orientation, giving 1440×1920 upright output on a portrait phone. The existing optional minimum zoom and `resizeMode: none` preference remain. Preview/capture use the full delivered frame with `contain`; there is no CSS zoom or forced center crop.
- [Apple's media capture delegate](https://developer.apple.com/documentation/webkit/wkuidelegate/webview(_:requestmediacapturepermissionfor:initiatedbyframe:type:decisionhandler:)) and [capture authorization guidance](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media) support handling the website decision separately from iOS authorization. The old delegate always returned `.prompt`. The new Snapchat path checks the requested iOS camera/microphone authorization and grants only an allowed, visible, HTTPS main-frame chat. Existing denials remain denials; other origins cannot inherit permission.

## Viewer and export findings

Inspected the public Snapchat web client returned on October 26, 2026: version 13.79.0, production build `2aa6cf7d`, [JavaScript bundle](https://cf-st.sc-cdn.net/dw/14a374cb957e6774b9f0.js) and [stylesheet](https://cf-st.sc-cdn.net/dw/eceeacedbecc23dae201.css). No authenticated account or messages were accessed.

The current lightbox retains the `S4e9r/ecBYF/RdKti/vDdE2/b2f4R` structure. Its actual `JGXlA/dCE9D` media layers also have sizing rules and inline desktop dimensions. Sizing just the outer player is insufficient. The repair removes the underlying chat from the viewer grid and expands those actual media layers while containing the full image/video. The regression fixture now reproduces the inner-layer desktop dimensions.

[Snapchat explains](https://help.snapchat.com/hc/en-gb/articles/7012354501524-When-I-save-a-Snap-in-Chat-where-is-it-stored) that Save in Chat stores media on its servers and that saved snaps can be exported to Camera Roll. Its current web chat menu exposes save/reply/reactions but lacks that export action. Vigil adds an explicit **Save to Camera Roll** button for opened photos and captured-photo previews. It composes original image pixels and separate image caption/sticker layers, checks that every layer is approved, and sends the PNG through the existing document-scoped native bridge.

Native export rechecks foreground access, current document/media identity, and content classification before writing with [Photos add-only authorization](https://developer.apple.com/documentation/photos/phaccesslevel/addonly). Photos permission denial produces a retryable message. Sensitive/unknown media, stale sources, away/screenshot shields, live camera streams, and background services cannot export. The new export is for photos; video viewing retains the full-screen sizing repair. PNG exports are bounded to 32 MiB and 80 million pixels.

## Validation

- Nine focused iOS simulator tests cover remembered authorization and denial, trusted-origin boundaries, the real web-to-native-to-Photos path, a real add-only Photos write, exact portrait edge pixels, caption/sticker compositing, blocked/stale exports, save retries, full-screen viewer/reply camera, chat/reply controls, and authentication handoff.
- Generated-stream tests emulate WebKit's primary-orientation behavior and exercise 320, 390, and 430 point widths. They verify the actual captured portrait pixels rather than inferring correctness from CSS. A retained XCTest image attachment provides visual evidence of the complete portrait frame.
- Seven runtime suites cover Snapchat media/authentication/coexistence and social build/container/route/orientation behavior. Runtime build, source lint, and the combined iPhone target compilation are checked separately.
- The existing `testSnapchatGroupChatRecoversRealFocusWithoutRemovingPrivacyScreen` test times out at its initial focus/presence transition. The same failure was reproduced against an unmodified HEAD snapshot in `/tmp/vigil-snapchat-native-baseline`; its implementation was not changed for this repair.
- Standalone Electron fixture runs exited early/SIGKILL, so they are not reported as passing. Vigil enforcement was not modified to run them. The native WebKit fixtures provide the browser validation above.

Physical camera field of view, the authenticated Snapchat service, and phone deployment remain for the user-requested final device update. No phone update, policy replacement, supervision operation, or app-only installation was performed during this repair. Existing unrelated YouTube edits and release metadata are excluded from the Snapchat commit.
