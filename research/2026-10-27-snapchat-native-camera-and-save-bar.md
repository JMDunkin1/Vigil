# Snapchat native camera and visible photo export

The October 26 constraint-based repair did not solve the physical phone's portrait framing or camera switching. Its synthetic input assumed a particular WebKit rotation behavior and therefore did not establish hardware correctness. This change replaces that acquisition path rather than adding another size or zoom adjustment.

The paired device record identifies an iPhone 17. [Apple's camera engineer explains](https://developer.apple.com/forums/thread/813548) that this generation has a differently rotated front sensor. [RotationCoordinator](https://developer.apple.com/documentation/avfoundation/avcapturedevice/rotationcoordinator) supplies the camera-specific angle; [videoRotationAngle](https://developer.apple.com/documentation/avfoundation/avcaptureconnection/videorotationangle) physically rotates video-data-output buffers. The iOS 27 SDK additionally provides an angle relative to a specified device orientation. The native path uses the portrait-relative angle, supported dynamic 3:4 framing on square sensors, and physical camera inputs. It disables Center Stage while capturing so automatic reframing cannot tighten the image, then restores the preceding Center Stage setting when capture stops.

`SnapchatCameraCapture` owns AVFoundation on one serial queue. Camera changes stop the old session before creating the next input/output. Exact camera IDs resolve to exact physical devices; a missing rear camera cannot silently fall back to the front. Every request and frame carries a fresh token, so late frames and old stop requests cannot affect the newly selected camera. The capture path waits for real portrait buffers, scales the entire image proportionally, and drops obsolete or backlogged frames. It does not crop a landscape frame into portrait.

The small, document-scoped WebKit bridge exposes those buffers through a fresh canvas-backed MediaStream for each selection. Snapchat keeps its ordinary shutter, caption, sending, and recording flows. Microphone capture remains WebKit's original audio stream. The removed path no longer opens an extra detached video consumer, reapplies zoom/size constraints, or relies on the browser's camera-device mapping. Intentional camera replacement follows normal `track.stop()` semantics, avoiding spurious capture-failure `ended` events; native/background termination still ends the generated track. The bridge is available only to the allowed, visible, current Snapchat main document, and capture stops when access is suspended or the document changes. Existing content filtering continues to classify the visible video; there is no native preview overlay around it.

The frame transport is bounded to one frame in flight, 20 frames/second, and a maximum 1440-pixel long edge. Encoded frames are transient and are not written to disk. This is a performance/quality tradeoff of the public WebKit bridge; physical-device latency and thermal behavior still need measurement.

## Save to Camera Roll

The old control lived inside Snapchat's React-owned media tree and depended on a narrow wrapper match. It could be absent or lost on remount, and it was not part of Snapchat's own save/reaction menu.

The replacement is a fixed native **Save to Camera Roll** button in a 44-point bar at the very bottom of the Snapchat view, above the home-indicator area. It stays visible in chat, camera, and photo views. Tapping it resolves the currently opened photo; with no photo open, it says **Open a photo first**. It also reports loading/unavailable, saving, failure, and confirmed Photos completion. The action calls the export function directly, without synthesizing a page click. The DOM lookup supports the player's media region without requiring the previous exact grid path. Native access checks, source identity, media classification, privacy shields, and Photos add-only authorization remain required. This exports opened photos and captured-photo previews, including image caption/sticker layers; it does not add video export.

## Evidence and limits

- Native WebKit tests exercise real decoded JPEG pixels and real canvas video across six front/back/ultrawide switches, stale-frame delivery, overlapping requests, old-track stops, and missing-camera errors. Native catalog/token tests verify exact-lens selection and stale-stop rejection. Separate tests reject unconfirmed documents before capture.
- The visible native button was pressed through its actual UIKit action. The test saved to the simulator's real Photos library and confirmed the completion message. A retained XCTest attachment shows the bottom bar's location. Existing portrait-layout, reply, export-pixel/privacy, authorization, and chat regressions remain covered.
- Node tests cover native camera enumeration, device identity, switch races, source cleanup, external termination, microphone isolation, permission errors, and origin/route/desktop boundaries. The combined iPhone target and runtime/lint/type checks are validated separately.
- The physical phone was not available for live inspection during this work. No physical capture, frame-rate/thermal measurement, authenticated snap transmission, or installed-device verification is claimed. No phone update or policy/supervision mutation was performed; deployment remains deferred under the user's earlier instruction.

The prior camera-orientation conclusion is superseded by this native implementation. Other chats' Instagram/YouTube edits and release metadata are excluded from this change set.
